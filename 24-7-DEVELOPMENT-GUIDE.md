## 1. Solo + automation: how “24/7” works when it’s just you

- **You** work in the time you have; you don’t work 24/7.
- **Automation** runs around the clock: CI on every push, scheduled jobs (e.g. Tracker weekly run), and scripts that update status or send notifications.
- **Context is king:** When you come back after school or a break, everything you need is in the repo — status, tasks, “what’s missing,” and where each project stands. No guessing.

So “24/7” here means: **the system and the docs are always up to date and ready for you;** when you’re not there, automation keeps things running and can notify you if something needs attention.

---

## 1b. Recommendation: automation 24/7 non-stop as main priority

If **automation 24/7 non-stop** is your main priority, do **not** depend on your computer or Cursor being on. Put everything in **hosted services** that run regardless of your laptop.

**Recommended setup (in order):**

1. **CI 24/7 (GitHub Actions)**  
   On every push (and optionally on a schedule): run build, run tests, run the gaps-check script and write GAPS.md (or a GAPS artifact). No machine of yours needs to be on. GitHub runs it.

2. **Scheduled jobs 24/7 (GitHub Actions or a tiny cloud worker)**  
   - **Tracker weekly report:** A scheduled workflow (e.g. “every Monday 8am”) that runs the Tracker pipeline (collect → gap report → response schema → build report) and posts to Slack.  
   - **Gaps-check on a schedule:** e.g. every night or every 6 hours, run the gaps-check and commit GAPS.md or post a digest to Slack.  
   Use GitHub Actions’ `schedule:` (cron) for this so you don’t need a server. If the Tracker needs a DB or long runtime, use a small always-on service (e.g. Railway, Render, or a $5 VPS) that only runs the cron script.

3. **Notifications**  
   - On **build/test failure:** GitHub Action sends to Slack (or email).  
   - On **scheduled run complete:** Optional message (“Tracker report sent” or “GAPS check done – 2 items”) so you see that automation ran.

4. **Status “Live” section**  
   A small script or Action that, after each workflow run, updates the “Live” part of STATUS.md (or a `status-live.json`) with last build time, last Tracker run, and link to GAPS. So when you open the repo, you see current state without your computer ever having been on.

5. **Your computer and Cursor**  
   Use them only when **you** are coding. When you’re done, push; CI and scheduled jobs do the rest. No need to leave your machine on or use a cloud dev box for “automation 24/7.”

**What you get:**  
- Builds and tests run 24/7 on every push.  
- Tracker weekly report (and any other cron) runs on schedule.  
- GAPS stay up to date from automated checks.  
- You get notified when something fails or when a run completes.  
- All of this works with your laptop closed.

**If you later want “AI producing code” 24/7:** Add a second layer: a VPS (or similar) + a headless agent that reads TASKS.md, calls an AI coding API, applies edits, and commits. Do that **after** the above is in place; automation 24/7 first, then optional code-production agent.

**Summary:** For automation 24/7 non-stop as the main priority, **recommendation = hosted automation first (GitHub Actions + scheduled workflows + notifications).** No home computer, no Cursor, no VPS required for that. Add a cloud machine or headless agent only if you want automated code production on top.

## 1c. Two-mode balance: Cursor when you’re here, handoff when you leave

A simple way to get balance: **when you’re at the computer, use Cursor normally; when your shift ends, run a keyword or command that hands off to the automation process.** After that, your machine can go off; automation runs 24/7 until you’re back.

**Mode 1 — You + Cursor (your shift)**  
- You work with Cursor as usual: code, run tests, update STATUS and HANDOFF.  
- No special setup; this is normal development.

**Handoff — one command when you leave**  
- When you’re done for the day (or before school, etc.), you run a **single command** that means “redirect to automation.”  
- That command does the handoff so automation can take over with the latest state.

**Mode 2 — Automation (after your shift)**  
- CI runs on the push from the handoff (build, tests, gaps-check).  
- Scheduled jobs (Tracker report, gaps-check, etc.) run on their schedule.  
- Notifications tell you if something failed or finished.  
- You don’t need your computer on; automation runs in the cloud.

**What the handoff command should do**  
1. **Save your context** — Update HANDOFF.md and STATUS.md (or open a small script that appends “End of shift” and “In progress: [next task]” so you don’t have to edit by hand every time).  
2. **Commit and push** — So the repo is up to date and CI runs.  
3. **Optional:** Trigger a workflow (e.g. GitHub Actions `workflow_dispatch` with a “handoff” input) so the first gaps-check or status update runs right away instead of waiting for the next schedule.

**Concrete options for the command**  
- **Option A — Script:** `./handoff` or `npm run handoff` — a script that (1) ensures HANDOFF and STATUS are updated (e.g. from env or prompts), (2) `git add` those files, (3) `git commit -m "handoff: end shift"`, (4) `git push`. Optionally it calls the GitHub API to trigger a “post-handoff” workflow.  
- **Option B — Keyword in commit message:** You manually update HANDOFF + STATUS, then commit with message `handoff` or `end shift`. A GitHub Action listens for that keyword (e.g. on push to `main` when the last commit message contains `handoff`) and runs the gaps-check or a “post-handoff” job.  
- **Option C — Alias:** You run `git add STATUS.md HANDOFF.md && git commit -m "handoff" && git push` (or an alias like `handoff` that does that). No script; the keyword is in the commit message so automation (or you) can see when you handed off.

**Ritual in one line:** When your shift ends, run your **handoff command** (script or commit + push with keyword). That’s the redirect to the automation process; after that, automation runs until you’re back and open Cursor again.

**Do you need a command when you come back?**  
You don’t *have* to — you can just open Cursor, read HANDOFF and STATUS, run the gaps-check, and pick a task. But a **resume (or “start shift”) command** keeps things symmetric and makes the “I’m back” ritual one step instead of several.

**What a resume command does**  
1. **Pull latest** — `git pull` so you have any commits from automation (e.g. GAPS.md or status updates from CI).  
2. **Run gaps-check** — So GAPS.md is up to date and you can review “what’s missing” right away.  
3. **Optional:** Open HANDOFF.md and STATUS.md in your editor so they’re the first thing you see.  
4. **Optional:** Notify something (e.g. “start shift” in Slack or a dashboard) — only if you want a record.

**Concrete option:** `./resume` or `npm run start-shift` — a script that runs `git pull`, then `./scripts/gaps-check.sh` (or `npm run gaps-check`), and optionally opens HANDOFF.md and STATUS.md. No push; you’re just syncing and loading context.

**Bookends:**  
- **Leave:** Run **handoff** → automation takes over.  
- **Come back:** Run **resume** → you’re synced and ready; then use Cursor as normal.

## 4. GAPS: automated “what’s missing” — part of “where you left off”

**NEW** **GAPS is automated.** You don’t fill it manually. A **gaps check** (script or CI job) runs and **writes** GAPS.md with what’s missing or failing. When you come back, you run the check and **review** GAPS to confirm everything is running correctly. That’s your “where you left off” quality step.

### 4.1 What runs the gaps check

A **gaps-check script** (e.g. `scripts/gaps-check.sh` or a Node/Python script) that:

1. **Runs tests** for each initiative (or a single test suite). Collects which tests failed and why.
2. **Runs smoke / completeness checks** (e.g. “Does GET /api/gap-report exist and return 200?” “Does the ProspectPortal ingest step run without error?”). Collects which checks failed.
3. **Writes GAPS.md** (or `gaps-output.md`) with a table: **Initiative | What’s missing / failed | Where (file or check name) | Priority**. Priority can be derived from the check (e.g. smoke failure = high; one unit test failed = medium).

You run this script **when you come back** (or it runs on every push / on a schedule in CI). The script overwrites or updates GAPS.md so it always reflects the **last run** of the check.

### 4.2 Example GAPS.md (auto-generated)

After a run, GAPS.md might look like:

```markdown
# GAPS — auto-generated (do not edit by hand)

Last run: 2025-02-24 15:00 UTC

| Initiative | What’s missing / failed | Where | Priority |
|------------|-------------------------|-------|----------|
| Tracker | GET /api/gap-report returned 500 | smoke check: gap-report-api | high |
| Tracker | Test "response schema generation" failed | tests/response-schema.test.js | medium |
| ProspectPortal | Ingest step not implemented | smoke check: ingest-url | high |
```

You **review** this when you come back: “Is everything running correctly?” If not, you fix the top row (or add a task) and re-run the check; GAPS updates automatically.

### 4.3 When you come back: run check → review GAPS

**NEW** 1. **Run the gaps check** (e.g. `./scripts/gaps-check.sh` or `npm run gaps-check`). Or open GAPS.md if the check already ran on push or on a schedule.
2. **Review GAPS.md** — Does anything need fixing? This is your “confirm everything is running correctly” step.
3. **Fix the top item(s)** and re-run the check so GAPS stays up to date. No manual logging.

### 4.4 Optional: add a line manually

If you notice something the automated check doesn’t cover (e.g. “copy on pricing page is wrong”), you can **append** one line to GAPS or keep a small “Manual” section. The script should **merge** or **append** to that instead of wiping it, so your manual note isn’t lost. For most gaps, the automated run is enough.

## 5. Real-time status: see updates on the app as they happen

You want to **see in real time** what’s going on (last build, last deploy, last Tracker run). STATUS.md can have two parts: **you-maintained** and **auto-updated**.

### 5.1 What STATUS.md contains

**Part 1 — You update (when you work):**

- Per initiative: **Phase**, **Done (last session)**, **Next**, **Blockers**.
- Short and honest; update at the end of each session.

**Part 2 — Real-time / auto-updated:**

- **Last build:** Time and result (e.g. “2025-02-24 14:30 — success” or “failed”).
- **Last deploy:** When the app was last deployed (if you have staging/production).
- **Last Tracker run:** When the weekly (or test) job last ran (if applicable).
- **CI badge or link:** So you can click and see the latest run.

This “Part 2” can be **filled by a script or CI** so you don’t have to remember to change it. For example:

- A **GitHub Action** (or cron) runs every hour (or on every workflow run) and rewrites a section of STATUS.md, or writes to a small `status-live.json`.
- Or a **script** (e.g. `scripts/update-status-from-ci.sh`) that fetches CI/deploy info and appends to STATUS.md or generates a “Live” block.

Then when you open STATUS.md (or a dashboard that reads it), you see **current** app state, not only what you wrote last night.

### 5.2 Example STATUS.md structure

```markdown
# Status — Three initiatives

## You-maintained (update at end of session)

Last session: 2025-02-24 evening

### Initiative 1: Tracker Bot
- **Phase:** Building gap report API
- **Done:** Schema in code; endpoint stub
- **Next:** Wire DB and return real gap list
- **Blockers:** None

### Initiative 2: ProspectPortal
- **Phase:** Not started
- **Next:** Set up repo and ingest step

### Initiative 3: Marketplace
- **Phase:** Discovery
- **Next:** Sync with coworker on API

---

## Live / auto-updated (do not edit by hand)

*This section is updated by CI/scripts.*

- **Last build:** 2025-02-24 14:35 UTC — success — [View run](https://github.com/.../actions/...)
- **Last deploy (staging):** 2025-02-24 12:00 UTC
- **Last Tracker run:** 2025-02-24 08:00 UTC (weekly job)
- **CI:** green
```

The “Live” section can be generated by a small job (e.g. GitHub Action that runs on `workflow_run` or on schedule and uses the API to get last run time, then writes to the file or to a JSON that a simple dashboard reads).

### 5.3 Optional: simple status dashboard

If you want a **page** that shows real-time updates:

- **Option A:** A single HTML file (e.g. `status.html`) that shows “Last build,” “Last deploy,” “Last run,” with timestamps. A script or CI step writes a `status-live.json`; the HTML loads it and refreshes every N seconds.
- **Option B:** A Notion or Google Doc that you (or a script) update with the same info; you open it on your phone or laptop to “see status in real time.”

Even without a dashboard, **STATUS.md with an auto-updated “Live” section** already gives you real-time visibility when you open the repo.

## 6. Notifications: turn status into alerts

So you don’t have to open the repo to know when something needs attention.

### 6.1 What to get notified about

| Event | Why |
|-------|-----|
| **Build failed** | Fix or run gaps check; GAPS will auto-update with failures. |
| **Build succeeded** (optional) | Reassuring when you’re away. |
| **Deploy completed** (optional) | Staging/production is updated. |
| **Scheduled job ran** (e.g. Tracker weekly run) | Confirm automation is working. |
| **Gaps check found failures** (optional) | When the gaps-check script runs (e.g. in CI) and writes new items to GAPS; you get a digest so you know to review. |

### 6.2 How to get notifications

**Slack or Discord (recommended):**

1. Create an **incoming webhook** (Slack: Incoming Webhooks; Discord: Webhook in channel settings). Copy the URL.
2. In your repo: add the URL as a **secret** (e.g. `SLACK_WEBHOOK_URL`).
3. In **GitHub Actions:** add a step that runs on failure (or on success, or on schedule) and sends a POST to the webhook with a short message (e.g. “Tracker Competitors Bot: build failed on main — [link to run]”).
4. You’ll get a message in that channel when the event happens.

**Email:**

- Turn on **GitHub notification** for “Actions” (e.g. “Send email on workflow failure”). No extra setup; you get an email when a workflow fails.

**Example (GitHub Action step for Slack on failure):**

```yaml
- name: Notify on failure
  if: failure()
  run: |
    curl -X POST -H 'Content-type: application/json' \
      --data "{\"text\":\"Tracker Bot: build failed — ${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}\"}" \
      "${{ secrets.SLACK_WEBHOOK_URL }}"
```

You can add a **scheduled workflow** that runs once a day and posts a short “status digest” (e.g. “Last build: green. Last Tracker run: today 8am. GAPS: 2 items.”) to the same webhook so you see updates even when nothing failed.

## 10. Common questions

### Wouldn’t it be better for each app to have different repositories?

**It can be.** Here’s the tradeoff:

| Approach | Pros | Cons |
|----------|------|------|
| **One repo (monorepo)** | Single clone; shared docs (PRD, ACTION-PLAN, 24-7 guide); STATUS/HANDOFF/GAPS apply to all; one CI can run gaps-check for both. | Tracker and ProspectPortal code live together; you must separate by folder and avoid coupling. |
| **Separate repos** (e.g. `tracker-bot`, `prospectportal`) | Clear ownership per product; independent CI, deploy, and versioning; no risk of one app breaking the other. | You have 2 (or 3) repos to clone, push, and keep in sync; STATUS and HANDOFF either live in one “meta” repo or you duplicate the 24-7 ritual per repo. |

**Recommendation for you (solo, two products):**

- **If you want clean separation and might deploy or share one app without the other:** use **separate repos** for Tracker and ProspectPortal. Keep this repo (or a small “meta” repo) for **docs only**: PRD, ACTION-PLAN, 24-7 guide, STATUS, HANDOFF, and links to the two app repos. Then each app repo has its own TASKS.md, CONTEXT.md, and CI; you run the gaps-check per repo or from the meta repo.
- **If you prefer one place and one clone:** keep a **monorepo** with `tracker/` and `prospectportal/` (or under initiative folders). STATUS/HANDOFF/GAPS stay at root; each app has its own package.json and tests. CI runs both apps’ tests and one gaps-check that knows both paths.

So: **yes, separate repos can be better** for two distinct apps, especially if you’ll deploy or open-source one without the other. If you stay in one repo, keep app code in separate folders and one shared doc layer.

### Is Cursor going to code 24/7 even if my computer is closed?

**No.** Cursor runs **on your machine**. When your computer is off or asleep, Cursor is not running, so nothing is coding or editing files.

What **can** run 24/7 without your computer:

- **GitHub Actions (or other CI):** Builds, tests, and workflows run on GitHub’s servers on every push or on a schedule. So “run tests at 2am” or “run gaps-check every night” works.
- **Scheduled jobs in the cloud:** If you deploy the Tracker to a server or use a serverless cron (e.g. “every Monday 8am run Tracker and post to Slack”), that job runs even when your laptop is closed.
- **Notifications:** CI can send Slack/email when a build fails, so you see results when you’re away.

So “24/7” in this guide means: **(1)** when you’re at the computer, the **docs and tasks** let you pick up quickly; **(2)** when you’re not, **automation** (CI, scheduled jobs, notifications) can run on **hosted** infrastructure. Cursor itself does not run when your computer is closed.

**If you want Cursor (or an AI coding agent) to be producing code 24/7 non-stop:** then yes — the machine where Cursor runs must be **on and running** with Cursor (or the agent) active. That typically means either **(a)** your computer at home left on and open on your desk (or in a corner) with Cursor running and an automated/agent session doing tasks from your task list, or **(b)** a **cloud dev machine** — see the expanded section below.

A **cloud dev machine** is a computer in a data center that stays on 24/7. You use it so that coding (or an agent) can run there instead of on your laptop. Your laptop can be closed; the cloud machine keeps working.

#### What you can use

#### How Cursor fits in

- **Cursor with Remote SSH:** You install the Cursor (or VS Code) “Remote – SSH” workflow and point it at your cloud machine. When you **open Cursor on your laptop** and connect to the host, you’re editing code that lives on the cloud. The **code and repo** are on the cloud 24/7; **Cursor itself** (the UI and the AI) only run when you have that connection open. So the machine is on 24/7, but “Cursor producing” only happens while you’re connected — unless you add something else (see below).
- **Cursor or VS Code Server on the cloud:** Some setups let you run a “server” version of the editor on the VM and connect from a browser or client. If that server stays on and you (or a script) trigger an AI/agent session on it, then “producing” could happen without your laptop. This is less standard and depends on what Cursor/VS Code offer for unattended use.
- **Headless coding agent on the cloud:** Instead of the Cursor UI, you run a **script or service** on the VPS that: reads your TASKS.md (or a queue), runs an AI coding API (e.g. OpenAI, or a tool that drives Cursor’s API if available), applies edits, runs tests, and commits. That can run 24/7 on the VPS via cron or a long-running process. Your laptop can be off. This is “Option B” in its fullest form: the **cloud machine** is what’s producing 24/7, using automation + AI, not Cursor’s UI per se.

#### Setup in broad strokes (VPS example)

1. **Rent a small VPS** (e.g. DigitalOcean Droplet or Linode; 1 GB RAM is enough to start).
2. **Create a user, install SSH keys** so you can `ssh user@your-server`.
3. **Clone your repo** on the server; install Node/Python and any deps.
4. **Option A — Use it as your dev host:** On your laptop, in Cursor, use Remote – SSH and connect to the VPS. When you code, you’re editing on the server. The server stays on; you only connect when you’re working. No 24/7 “Cursor producing” unless you leave a session open or use a headless agent.
5. **Option B — Run a headless agent:** On the VPS, install a script (or use a tool) that: on a schedule or loop, picks the next task from TASKS.md, calls an AI API to generate a patch or next step, applies it, runs tests, commits, and pushes. That runs 24/7 without your laptop. You’d need to design or adopt such a script (e.g. a small Node/Python app that uses the OpenAI API or another coding API and git).

#### Pros and cons

| Pros | Cons |
|------|------|
| Your home computer can stay off; no extra power or wear. | Monthly cost ($5–20+ for a VPS; Codespaces/Gitpod can add up if left on). |
| Same environment every time (Linux, same paths); good for CI-like runs. | You have to maintain the box (updates, security, keys). |
| For a headless agent: true 24/7 code production without you at the keyboard. | Headless agent setup is custom; Cursor doesn’t officially “run unattended” in the cloud. |
| You can connect from anywhere (laptop, another PC) via SSH or Remote. | If the VPS goes down, 24/7 stops until you fix it or restart. |

#### Summary

**Option B = a machine in the cloud is on 24/7.** You can use it as a **remote dev host** (connect with Cursor when you work) or go further and run a **headless coding agent** there so code is produced around the clock without your laptop. The first is straightforward (VPS + SSH + clone repo + Cursor Remote); the second requires a script or service that drives an AI coding API and git. Either way, “Cursor producing 24/7” in the sense of “something coding for me non-stop” means that cloud machine is on and something (Cursor when you’re connected, or an agent when you’re not) is running there.
